## Fixed

1. **Unrequested second creation**: Make called `performVariation` automatically after a successful POST. The backend can debit MU credit for creations beyond the free allowance (`store/src/catalog.rs:6641–6657`). Now a second creation requires the explicit button (`ios/MU/Sources/Features/Make/MakeView.swift:1161–1165`). Japanese/English creation-cost descriptions now disclose the 3-free/¥100 contract, including variations/remixes. Production GET `/api/make/quota` returned `free_per_day=3`, `price_jpy=100`, `daily_cap=5` during this audit.
2. **Tab-switch result loss**: `onDisappear` previously cancelled the in-flight creation and invalidated its response, though the server could already be making it. Presentation suspension now stops microphone/preview/review work while retaining mutation responses (`MakeView.swift:1042–1048`). Returning to Make resumes preview reads. This does not promise persistence across process termination.
3. **Cold-start prompt handoff**: initial pending prompts could be missed by change-only observation. A consume-once path handles view initialization and catalog readiness (`MakeView.swift:1100–1105`).
4. **Stale search/filter responses, skipped failed pages, duplicate rows**: shared `ProductFeed` only accepts its latest request, advances page after success, and deduplicates SKU (`ios/MU/Sources/Core/ProductFeed.swift:38–56`). Both Live and Shop use it, with an explicit retry button.
5. **Search-clear did not reload**: Shop now searches after a 300 ms debounce and reloads immediately when cleared (`ShopView.swift:46–55`).
6. **Email/code edits racing login**: freeze inputs/restart while busy, snapshot and trim submitted values, guard duplicate submission (`ClosetView.swift:38–91`).
7. **AI creation failure was generic**: retain the actual API error, including registration/payment conditions (`AgentView.swift:190–194`). Stop voice capture on leaving Make/Agent.

### Creation-count and offscreen-completion tests (2026-09-17, second pass)

Watching for a second result row cannot detect a creation that is never displayed, so three UI tests assert the actual request counts. A DEBUG-only probe (`ios/MU/Sources/Core/MakeUITestFixture.swift`, `FixtureCounterProbe`) publishes `make` (POST `/api/make` issued), `delivered` (response delivered) and `peek` counts through `accessibilityValue`, rendered above the tab bar so it stays readable while Make is offscreen.

8. **Another account's design survived sign-out / account switching**: a design belongs to the account that created it, but nothing cleared it when the session identity changed, so the previous account's result, in-flight work and pending intent stayed on screen and could be acted on by the next account. `Session` now publishes an `identity` (`Session.swift:9-12`); `MakeView` clears designs, work and intents when a **logged-in** identity changes (`MakeView.swift`, `discardStateIfAccountChanged`). The first login (`nil -> email`) is deliberately excluded so the auth sheet can still resume its pending intent. `AgentView` resets on the same transition and rejects any reply belonging to a previous identity by capturing the API key and the identity generation at send time (`AgentView.swift`, `acceptsGeneration`).

### Account-isolation tests (2026-09-17, third pass)

`ios/MUUITests/AccountSwitchTests.swift` drives the real SwiftUI screen offline. Account changes are triggered by DEBUG-only, fixture-gated buttons (`FixtureAccountSwitcher`) rather than a shared file, because the UI test runner and the app run in separate sandboxes. They change memory only: no Keychain write and no network login.

| Test | Assertion | Evidence |
|---|---|---|
| `testSignOutClearsPreviousAccountDesign` | previous design disappears after sign-out | `mu-ios-audit-account.xcresult` |
| `testSwitchingAccountClearsPreviousDesign` | first account's design disappears after switching | same |
| `testLateCreationResponseDoesNotAppearAfterAccountSwitch` | a response that completes after the switch is never shown | same |
| `testFirstLoginThroughAuthGateResumesPendingCreation` | starts **signed out** (`MU_UI_FIXTURE_SIGNED_OUT=1`), cold prompt shows the AuthGate with `make == 0`, then an in-memory `nil -> email` login dismisses it and the pending creation runs exactly once (`make == 1`) | same |
| `testAgentReplyAfterAccountSwitchDoesNotCreate` | a delayed `/api/app/agent/chat` reply answering `action=make` is discarded after switching, so `make == 0` | same |

`testAgentFirstLoginMidFlightReleasesInputAndDiscardsOldAction` closes a regression found on review: the first login (`nil -> email`) also rotates the generation, but `AgentView` was clearing only when the previous identity was non-nil, so `sending` stayed `true` and the input bar remained permanently disabled. `AgentView` now resets on `identityGeneration`, which covers every authentication transition, and the test asserts the input becomes usable again while the pre-login reply is still discarded (`make == 0`).

`SessionIdentityTests` (unit) pins the generation contract: the generation rotates on every identity change, and returning to the same email (A -> B -> A) does **not** reuse the first visit's generation, which is why `AgentView` compares generations rather than email strings. A second unit test asserts the fixture account helpers are inert unless the fixture is enabled, so a normal device login cannot be faked.

The first-login test previously started already logged in and therefore proved nothing about the `nil -> email` path; it now walks the real AuthGate flow. The in-memory login writes nothing to the Keychain and sends no OTP.

The third test switches accounts while the fixture is still delaying the response, so it covers a completion arriving under the wrong account rather than only a state-clearing side effect.

`FixtureCounterProbe` and `FixtureAccountSwitcher` are `#if DEBUG` and fixture-gated. `nm -a` on the Release binary reports zero `MakeUITestFixture` / `FixtureCounterProbe` / `FixtureAccountSwitcher` / `logInForUITest` / `logOutForUITest` / `enableFixtureForUnitTest` symbols. `AgentView.resetForNewIdentity` does appear, which is intended: it is production logic that must also run on a real sign-out.

Production UI tests load the actual kinds catalog, select mug and wall_clock without fallback, open an actual Shop product, and verify its purchase URL host/path/SKU. They stop before clicking checkout. No live generation, payment, order, account deletion or verification email was initiated by the audit.
